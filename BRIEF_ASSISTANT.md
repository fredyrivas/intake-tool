# Intent-first brief intake

The product UI remains in English. The four screens are **Intent → Scope → Clarify → Review**.

## Analysis flow

1. **Intent / source reading:** send the intent and original documents, classify every document and extract facts with evidence. No field catalog or route criteria are sent.
2. **Intent / Scope preparation:** chain from the reading with `previous_interaction_id`; send Module 01 and route options with their relevant criteria. Return title, field and route proposals, plus questions for unresolved required Module 01 fields. Only route ambiguities are shown in Scope.
3. **Clarify:** confirming Scope makes no model call. The application computes unresolved required Module 01 fields and uses prepared questions or local fallbacks. Structured answers need no AI call. “Describe your answer instead” invokes the clarification task and presents suggestions for confirmation.
4. **Review:** chain from the latest interaction, summarize confirmed values and propose only currently active Module 02–04 fields. Suggestions require confirmation and never replace confirmed values. Optional fields revealed by accepting a parent choice can be completed in Review.

New documents use a dedicated enrichment task. Normally there are three Gemini calls; source recovery, free-text interpretation and additional documents can add calls without adding screens. The title is required; its generation criterion belongs in interpretation. The canonical project name is generated by the application. Explicit approver/reviewer emails may be proposed only with evidence identifying the role and address; reviewers remain optional.

## Configuration maintenance

| File | Edit here |
| --- | --- |
| `shared/brief-catalog.json` | Four ordered modules, fields, exact options, required defaults, templates and activation policies. |
| `shared/brief-interpretation.json` | General, field-specific and document interpretation criteria, including project title generation. |
| `shared/brief-system-instructions.json` | Common instructions, response guidance and the five task instructions; each block has an ID, title and English text. |
| `shared/brief-workflow.json` | Task-to-catalog selection, instruction/criterion references, automatic messages and shared response contracts. |

Define each rule once and reference its ID. Field-specific criteria are selected by the fields actually included in the task catalog. Shared schema references are expanded before sending a request; document role options come from the catalog. The server narrows response field IDs to the task catalog and validates the output again. Increment the edited document's version (`version.instruction` for interpretation) so saved interaction contexts are rebuilt when configuration changes. Do not add new business criteria as part of structural maintenance.

TypeScript retains conditional evaluation, required-field checks, prompt assembly, response validation, request sequencing and persistence. `server/brief-instruction.ts` assembles each task's instruction. `server/brief-analysis.ts` handles the local API; `src/brief-analysis-flow.ts` sequences calls and checkpoints.

## Context and recovery

The draft stores validated extraction, processed document fingerprints, configuration version, and the first/latest interaction IDs. Its payload version is 4; earlier drafts load with no interaction context. The existing browser storage key is retained for compatibility.

The reading checkpoint is saved before Scope starts, in browser storage or the existing saved brief. A failed Scope can reuse it. Changes to intent, removed/replaced documents or configuration versions rebuild the chain. New documents extend it. An unavailable provider interaction triggers one reconstruction from saved sources; other failures preserve the checkpoint and surface a retryable error. Confirmed application values remain authoritative in every request.

Vertex Interactions uses Application Default Credentials and the **global** endpoint, with `store: true`. System instructions, tools and generation configuration are explicitly supplied on every call. Previous interaction IDs avoid uploading the same contents again, but retained history is still model context and does not guarantee token savings. Google Cloud currently documents Interactions as Preview: https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/capabilities/interactions

PPTX text and embedded images retain slide locators; XLSX extraction retains sheet/cell references. PDF and image inputs remain native multimodal content. Search is limited to retailer verification; web evidence is accepted only from provider URL citations. Sources and context are also stored with saved local briefs and browser drafts.
